# Problem Query 03: Monthly Sequencing Runs By Manufacturer And Platform

## Initial Query

> Plot me a graph of the number of sequencing runs per month for the last 3 years by manufacturer and platform

## Approach I Took

I used only the MLWH MCP server surface for the initial data attempts. Since the query asks for a global time-series aggregate, I first looked for a global run listing or aggregate endpoint.

The main path was:

1. Call `mlwh_freshness` to confirm the mirrored run/product tables present in the cache.
2. Read the MLWH workflow/resource catalogue exposed by the MCP server.
3. Test the generic `mlwh_call_endpoint` escape hatch with `AllStudies`, which worked and showed `8217` mirrored studies.
4. Try obvious global run registry method names through `mlwh_call_endpoint`, including `AllRuns` and `RunSearch`.
5. Review the advertised routes available through the MCP server.

The cache clearly contains run-related mirrors for multiple technologies, including `iseq_flowcell`, `iseq_product_metrics`, `iseq_run_status`, `pac_bio_run_well_metrics`, `eseq_run`, `eseq_run_lane_metrics`, `useq_run_metrics`, `pac_bio_product_metrics`, `eseq_product_metrics`, and `useq_product_metrics`.

However, the exposed query surface did not include a global run list or a grouped run-count endpoint. `AllStudies` was available, but `AllRuns` and `RunSearch` were not registry methods.

## Problems With The MCP Server Offerings

The server has run tools only after the caller already knows a study id, sample name, or run id. Examples include `mlwh_runs_for_study`, `mlwh_run_overview`, `mlwh_run_status`, and `mlwh_samples_for_run`. There is no endpoint for "all runs since date X".

There is no endpoint that returns one row per sequencing run with a run date, manufacturer, platform, and stable cross-platform run identifier. Without that, I could not count runs per calendar month.

The exposed run fields are also not enough for the requested grouping. The MCP responses commonly expose `platform` in path/progress contexts, but I did not find an exposed `manufacturer` field suitable for grouping. The table names imply sources such as Illumina, PacBio, Element, and Ultimagen, but deriving manufacturer from table names is not an MCP-supported query result.

The current run overview is Illumina-oriented because it takes an Illumina NPG run id. Cross-platform status appears through `mlwh_sample_progress`, but that requires starting from sample names and is not suitable for global run aggregation.

The "last 3 years" range is date-sensitive. On the date of this attempt, that means roughly `2023-07-02` through `2026-07-02`, but the cache freshness showed most relevant mirrors last synced on `2026-07-01`. A correct server-side aggregate should make the effective cache cutoff explicit.

## Attempted Workarounds

The only possible workaround using current tools would be to page all `8217` studies, call `mlwh_runs_for_study` for each, deduplicate run ids, call `mlwh_run_status` or `mlwh_run_overview` for each run, infer dates, and then build the plot locally.

That workaround is not reliable. Runs can belong to multiple studies, cross-platform run identifiers are not consistently exposed, non-Illumina run status is not directly queryable by run id, and manufacturer would still have to be inferred rather than read from a response field.

I did not generate a graph because there was no trustworthy dataset to plot from the MCP server's exposed operations.

## Remaining Doubts

"Number of sequencing runs per month" could mean month of run start, run completion, QC completion, archival, or first data added to iRODS. The current tools expose several timestamps in different contexts, but no global definition for this aggregate.

"Manufacturer" and "platform" may be separate warehouse fields, or manufacturer may need to be derived from the platform/source table. The MCP surface did not expose enough metadata to decide.

Cross-platform run identity is unclear. Illumina has numeric NPG run ids, while Ultimagen sample progress currently reports `id_run: 0` and embeds native-looking run names only in iRODS paths.

## Improvement Ideas

Add a global aggregate endpoint such as:

`GET /runs/monthly-counts?since=2023-07-02T00:00:00Z&until=2026-07-02T00:00:00Z&date_basis=run_start&group_by=manufacturer,platform`

The response should include month, manufacturer, platform, count, date basis, and cache sync timestamp.

A lower-level global run listing would also help:

`GET /runs?since=...&until=...&platform=...&limit=...&offset=...`

Each row should include a stable run identifier, native run identifier, platform, manufacturer, run-start timestamp, run-complete timestamp when available, archived/data-added timestamp when available, and enough source metadata to deduplicate across studies.

The server should document the recommended date basis for operational run-count charts. If multiple bases are valid, make the caller choose explicitly.
