# Problem Query 04: Latest Illumina Data Locations For MAVE Studies

## Initial Query

> Find me the locations for the latest Illumina run data for any MAVE studies

## Approach I Took

I used only the MLWH MCP server surface for the initial data attempts. I interpreted "MAVE studies" as studies returned by the study substring search for `MAVE`, because the server does not expose a first-class project tag or programme concept called MAVE.

The main path was:

1. Search studies with `mlwh_search_studies(term="MAVE")`.
2. Confirm there were `7` matching studies with `mlwh_count_studies_search`.
3. Call `mlwh_study_overview` for each matching study.
4. Keep only studies with runs/data: `7135`, `7258`, and `8248`.
5. Call `mlwh_runs_for_study` and `mlwh_count_runs_for_study` for those studies.
6. Compare high-end candidate runs with `mlwh_run_overview`.
7. Use `mlwh_irods_paths_for_run` and `mlwh_count_irods_paths_for_run` for the latest candidate run.
8. Use `mlwh_study_manifest` with `with_irods=true` and `file_type=cram` near the end of the MAVE study manifest to recover study-scoped sample/path rows for that run.

The `MAVE` search returned these study ids:

- `7135`: `MAVE_SGE v0.2.1`
- `7258`: `MAVE SGE Plasmid QC`
- `7362`: `MAVE SGE Plasmid QCv3`
- `7364`: `MAVE_SGE v0.3.1`
- `8248`: `MAVE SciOps R&D`
- `8249`: `MAVE SciOps Production`
- `8324`: `MAVE SciOps Production Plasmid`

Only `7135`, `7258`, and `8248` had run/data counts in `mlwh_study_overview`. The latest candidate was study `7135`, whose overview reported `newest_data_added: 2026-06-27T16:16:43Z`.

For candidate run overviews:

- Run `52557` had `sequencing_date_range.latest: 2026-06-27T16:16:43Z`.
- Run `52541` had `sequencing_date_range.latest: 2026-06-25T15:39:47Z`.

- Run `51286` had `sequencing_date_range.latest: 2025-11-07T17:50:44Z`.

`mlwh_run_status(52557)` confirmed this was an Illumina run. `mlwh_count_irods_paths_for_run(52557)` returned `74` data objects.

The run-level path endpoint returned locations such as:

## Problems With The MCP Server Offerings

The server can find likely MAVE studies through substring search, but it does not expose a canonical MAVE project/group resolver. The search result may include studies that mention MAVE in different operational contexts.

There is no direct endpoint for "latest Illumina iRODS locations for studies matching this term". The answer required combining study search, study overview, runs-for-study, run overview, run status, run iRODS paths, and study manifest.

`mlwh_irods_paths_for_run` is run-scoped, not study-scoped. Run `52557` had `74` iRODS objects and `2` studies, so the run path list alone could include non-MAVE rows. For the first returned rows, `name` was empty and `id_sample_tmp` was `0`, which made the run path list less useful for sample-level reporting.

`mlwh_study_manifest` is study-scoped and carries sample/supplier/path fields, but it has no `run_id` filter. I had to rely on its documented sort order and page near the end of a `7524` row manifest to find run `52557`.

The manifest rows do not expose the iRODS `created` timestamp. I could identify `52557` as the latest run by `mlwh_run_overview`, but I could not prove from the manifest rows themselves that each listed path shared the latest iRODS timestamp.

## Attempted Workarounds

I used `mlwh_study_overview.newest_data_added` to shortlist MAVE studies and `mlwh_run_overview.sequencing_date_range.latest` to compare candidate runs.

I used `mlwh_run_status` to confirm the latest candidate was Illumina.

I used `mlwh_irods_paths_for_run` to get the run-level location pattern and count, then `mlwh_study_manifest` to recover MAVE study-scoped sample and supplier fields for the same run.

This was a workable manual route, but it was not efficient or robust enough for a polished user-facing answer with every latest location.

## Remaining Doubts

"Latest Illumina run data" could mean latest iRODS data creation, latest run start, latest run archived, latest QC completion, or latest NPG run id. I used iRODS data creation via `run_overview.sequencing_date_range.latest` because the user asked for locations.

Run `52557` spans two studies, and the run-level path list is not study-scoped. The manifest confirmed MAVE rows for the run, but a complete answer would need to page all run `52557` manifest rows for study `7135`.

If "MAVE studies" should mean only a curated subset, active studies, production studies, or studies owned by a specific team, the substring search may be too broad.

## Improvement Ideas

Add a direct endpoint such as:

`GET /search/study/:term/latest-irods?platform=Illumina&file_type=cram&limit=...`

or:

`GET /study/:id/irods/latest?platform=Illumina&file_type=cram&limit=...`

The response should include `created`, study id, study name, run id, platform, sample name, supplier name, lane, tag index, and `irods_path`, sorted by `created DESC`.

Add a `run_id` filter to `mlwh_study_manifest`, so callers can request study-scoped locations for a known run without paging through thousands of unrelated product rows.

Add a study-scoped run-iRODS endpoint:

`GET /study/:study/run/:run/irods`

That would avoid mixing rows from other studies on shared runs.

Finally, add a canonical project/tag resolver if terms like `MAVE` are expected to be operationally meaningful beyond substring search.
