# Problem Query 05: Genotype Checks For Ultima IBD Studies

## Initial Query

> What information do we have for genotype checks ("gt" perhaps) in the mlwh database for Ultima sequencing, especially for "IBD" studies?

## Approach I Took

I used only the MLWH MCP server surface for the initial data attempts. I treated "Ultima" as the platform label `Ultimagen`, because that is the spelling exposed by the MCP responses.

The main path was:

1. Search studies for `IBD` with `mlwh_search_studies` and count matches with `mlwh_count_studies_search`.
2. Search studies and samples for `genotype`.
3. Try the user's suggested `gt` term in study and sample search.
4. Try exact library-type lookup for `gt`.
5. Inspect likely IBD/genotyping study ids with `mlwh_study_overview` and `mlwh_study_status_breakdown`.
6. Follow the strongest IBD-plus-Ultimagen hit into iRODS paths and sample progress.

The broad searches found:

- `mlwh_count_studies_search(term="IBD")`: `72` studies.
- `mlwh_count_studies_search(term="genotype")`: `14` studies.
- `mlwh_count_samples(term="genotype")`: `30` samples.
- `mlwh_search_studies(term="gt")` and `mlwh_search_samples(term="gt")`: rejected because the minimum search term length is `3`.
- `mlwh_find_samples(field="library_type", value="gt")`: identifier not found.

## Problems With The MCP Server Offerings

The MCP server does not expose schema or table search. I could not ask "which MLWH tables or columns contain `gt`, `genotype`, or genotype-check data?"

The regular search endpoints only search selected study or sample metadata fields. They can find studies or samples whose names/titles/supplier names mention `genotype`, but they do not search warehouse columns, pipeline result names, QC annotations, or genotype-check tables.

The literal term `gt` cannot be searched through the text search tools because the minimum term length is three characters. Exact lookup by library type `gt` found nothing.

The server exposes useful QC roll-ups, but not genotype-check details. `mlwh_study_status_breakdown` gives counts for `qc_pass`, `qc_fail`, and `qc_pending`; `mlwh_sample_progress` gives a sample-level `qc` value. Neither gives genotype concordance, check type, expected genotype id, observed genotype id, failure reason, check timestamp, operator/manual status, or pipeline output location.

Ultimagen support is present but indirect. Study iRODS paths can show `platform: Ultimagen`, and sample progress can show Ultimagen run-status timelines. However, the run id is reported as `0`, and there is no direct `mlwh_run_overview`, `mlwh_run_status`, or `mlwh_irods_paths_for_run` route for a native Ultimagen run identifier.

Two zero-data IBD/genotype-looking studies, `5990` and `8338`, caused `mlwh_study_status_breakdown` tool-output validation errors because `per_platform` came back as `null` where the tool schema expected an array. `mlwh_study_overview` handled those studies and reported zero samples/runs/data, so this looks like a response-shape bug in the status-breakdown path for empty studies.

## Attempted Workarounds

I used broad metadata search to locate IBD studies and genotype-related studies, then manually sampled likely relevant study ids.

I used `mlwh_study_status_breakdown` as the only compact way to detect whether a study had `Ultimagen` data. That identified study `7682` as a strong IBD-plus-Ultimagen case.

I used `mlwh_irods_paths_for_study` to verify that study `7682` really had Ultimagen paths in `/seq/ultimagen/...`.

I used `mlwh_sample_progress` and `mlwh_sample_detail` for `7682STDY15067863` to inspect the deepest exposed per-sample Ultimagen information. That provided platform, QC roll-up, delivery time, run-status events, and iRODS directories, but not genotype-check records.

## Remaining Doubts

I cannot tell whether "genotype checks" refers to a specific MLWH table, a pipeline output, a QC flag, a manual QC concept, a library/sample naming convention, or a downstream analysis outside the mirrored cache.

I cannot reconcile the study `7682` distinct sample count of `507` with the much larger Ultimagen per-platform ladder counts from `mlwh_study_status_breakdown`. The endpoint documentation says per-platform totals may exceed the distinct sample total for multi-platform samples, but the size of the difference suggests either product-level counting, repeated Ultimagen products per sample, or another platform-specific denominator that needs clearer labelling.

The sample `7682STDY15067863` appears in study-scoped iRODS paths for `7682`, but the sample detail response did not include study/library arrays for it. That may be expected for the way Ultimagen data is linked, but it makes the study/sample relationship harder to explain confidently.

"IBD studies" is broad. The search returned historical, active, pending, human, microbial, genotyping, WES, RNA, metagenomics, and single-cell studies. A better answer would need a more precise IBD scope or a server-side filter.

## Improvement Ideas

Add schema discovery for the MLWH cache, for example:

`GET /schema/search?term=gt`

or a curated domain endpoint:

`GET /genotype-checks?study_term=IBD&platform=Ultimagen`

A genotype-check response should include study id, sample name, supplier name, platform, native run id, check type, genotype/check status, concordance or score fields, expected/observed identifiers, failure reason, manual QC fields if present, timestamps, and any output paths.

Expose native Ultimagen run identifiers as first-class resolvable run ids. Then add run overview, run status, and run iRODS path tools for Ultimagen rather than requiring callers to start from samples or parse iRODS paths.

Allow exact short-token searches for controlled terms like `gt`, even if free-text prefix search still requires at least three characters.

Fix `mlwh_study_status_breakdown` so empty studies return `per_platform: []` rather than `null`, matching the advertised tool schema.

Clarify the denominator used by `per_platform` counts, especially for Ultimagen. If counts are product-grained, the field names should say so; if they are sample-grained, the output for study `7682` needs investigation.
