# Problem Query 06: PacBio Sequencing By Programme, Then A Per-Study Owner/Manager/Follower Table

## Initial Query

This was a three-turn conversation:

> Give me a breakdown of Pacbio sequencing by "programme" for the last year.

> That seems like a lot of Human Genetics I was not expecting. What are the 5 studies?

> Ok give me another table with a row for each study covering all programmes - add columns for the programme, the faulty sponsor, the study "owner"s, the study "manager"s, and the study "follower"s.

## Approach I Took

I used only the MLWH MCP server surface for the initial data attempts. I treated "programme" as the `programme` field on the study object, "Pacbio" as the canonical platform label `PacBio`, and "faulty sponsor" as the `faculty_sponsor` field.

The main path was:

1. Confirm `programme` is a real, readable field. `mlwh_resolve_study(7568)` returns `programme: "Human Genetics"` and `faculty_sponsor: "Carl Anderson"`. `mlwh_all_studies` rows also carry `programme` (values seen include `Other`, `Human Genetics`, `Cancer Genetics and Genomics`).
2. Look for any way to enumerate "PacBio sequencing for the last year" across all studies. Check every list/count tool for a platform filter and a date filter.
3. Establish the scale of a fallback fan-out: `mlwh_count_studies` returned `8223` studies.
4. For the per-study role table, probe the person/role tools. Call `mlwh_studies_for_user(person="Carl Anderson", role="follower")` and inspect `mlwh_study_detail(7568)`.

The useful facts found were:

- `programme` is populated on `Study` and is returned by `mlwh_resolve_study`, `mlwh_all_studies`, `mlwh_study_detail`, `mlwh_studies_for_user`, `mlwh_studies_for_faculty_sponsor`, and `mlwh_search_studies`.
- `mlwh_study_overview` — the cheap per-study aggregate that already carries `name`, `accession_number`, `faculty_sponsor`, and `data_access_group` — does **not** carry `programme`.
- There is no platform filter on any list or count tool, and no global run/product enumeration. The run tools (`mlwh_run_overview`, `mlwh_run_status`, `mlwh_irods_paths_for_run`) take an Illumina NPG run id only, so PacBio runs are not resolvable. The only date filter in the whole surface is `since`/`until` on `mlwh_samples_with_data_for_study` and its count, over the iRODS `created` timestamp, per study.
- `mlwh_studies_for_user` matches a person (name/login/email) and returns the studies they are a role member of, one row per `(study, role)`. `mlwh_studies_for_user("Carl Anderson", role="follower")` returned `5` studies, each row shaped `{role: "follower", study: {...}}`. The default role set (no `role` arg) is `owner, manager, data_access_contact`.
- `mlwh_study_detail(7568)` returns the study plus `sample_ids` and `library_ids`. Its `study` object keys are `accession_number, contains_human_dna, contaminated_human_dna, data_access_group, data_release_strategy, data_release_timing, ega_dac_accession_number, ega_policy_accession_number, ethically_approved, faculty_sponsor, id_lims, id_study_lims, id_study_tmp, name, programme, reference_genome, state, study_title, study_type, study_visibility, uuid_study_lims`. There is no `owner`, `manager`, `follower`, `study_users`, `role`, `login`, or `email` field anywhere in the response.

I could not produce the requested breakdown for the first turn, could not derive "the 5 studies" for the second turn from the tools alone, and for the third turn I could fill the `programme` and `faculty_sponsor` columns but not the `owner`, `manager`, or `follower` columns.

## Problems With The MCP Server Offerings

The first turn is blocked by the same wall as Problem Query 03: there is no global, platform-scoped, date-scoped sequencing enumeration. Nothing lets me ask "all PacBio sequencing in the last year". There is no platform filter, no global run or product list, no resolvable PacBio run identity, and the only date window (`since`/`until`) is per-study and over iRODS `created`. So "PacBio sequencing … for the last year" cannot be counted at all without touching every study.

`programme` is readable per study but is not an aggregation or grouping dimension. There is no "list studies by programme" route and no grouped count endpoint, so "breakdown … by programme" has to be assembled study by study. Worse, the one cheap per-study aggregate that would carry the platform/date/availability numbers — `mlwh_study_overview` — omits `programme`, so even the per-study fan-out needs a second call (`mlwh_resolve_study` / `mlwh_study_detail` / a page of `mlwh_all_studies`) just to read the grouping key. With `8223` studies, that is two calls per study to build one bar chart.

The third turn exposes a direction problem. The role information the user wants (owners, managers, followers) lives in `study_users`, and the only tool that reads it, `mlwh_studies_for_user`, goes **person → studies**. The user's table needs the inverse, **study → people**: given a study, list its owners/managers/followers. There is no `study/:id/users` route, `mlwh_study_detail` carries no user/role fields, and there is no people-directory endpoint to iterate (`mlwh_resolve_person` needs a search term, `mlwh_studies_for_user` needs a person). So a study's role membership is effectively not queryable from the study.

The two "person" concepts are also split. `faculty_sponsor` (the "faulty sponsor" column) is a free-text PI name on the `Study` object and is trivially readable, but the documentation is explicit that the faculty sponsor is NOT a `study_users` role. Owners/managers/followers are `study_users` rows reachable only person-first. So one of the four requested people-columns comes from one place (easy) and the other three come from a route that runs the wrong way (impossible from the study).

## Attempted Workarounds

For the `programme` and `faculty_sponsor` columns of the third-turn table, `mlwh_resolve_study` or a page of `mlwh_all_studies` gives both fields per study in one call, so those two columns are answerable for any known set of studies.

For the owner/manager/follower columns, the only conceivable workaround is to guess candidate people — the faculty sponsor, the logins embedded in `data_access_group`, or names from `mlwh_resolve_person` — then call `mlwh_studies_for_user` for each candidate and keep the rows whose study matches the target. That is brittle and cannot be complete: anyone who is an owner/manager/follower but was not guessed is silently missed, and there is no way to enumerate the candidate set.

For the first-turn breakdown, the only route is a full fan-out over all `8223` studies: for each, call `mlwh_study_status_breakdown` (whose `per_platform` partition has a PacBio bucket) or `mlwh_samples_with_data_for_study` with a `since`/`until` window for "last year", then read `programme` from a second call, then sum by programme. I did not run this: at `8223` studies it is thousands of calls, the per-platform counts are sample-grained rather than a clean "PacBio run/sample in the window" figure, and the date window is iRODS-created rather than a run date, so the result would be neither reliable nor clearly defined.

## Remaining Doubts

I cannot tell what unit "PacBio sequencing" should count — runs, SMRT cells, samples, or products — nor what "the last year" is measured against — run date, iRODS `created`, or registration. The tools only offer iRODS `created`, per study.

I am not sure of the exact `programme` vocabulary. `programme` is searchable through `mlwh_search_studies`, but that search conflates `name`, `title`, `programme`, and `faculty_sponsor`, so it cannot be trusted as a clean "studies in programme X" filter.

I cannot confirm that "owner", "manager", and "follower" are exactly the stored `study_users` role spellings; the role vocabulary is an open pass-through, so the requested labels may or may not match the stored roles.

## Improvement Ideas

Add a study → users endpoint, the inverse of `/studies/user/:person`:

`GET /study/:id/users?role=owner,manager,follower`

returning `name`, `login`, `email`, and `role`. That makes the third-turn table one call per study and closes the direction gap.

Make `programme` a first-class dimension. A `GET /studies/programme/:name` list and a `GET /programmes` enumeration would replace the substring-search guess, and a grouped aggregate such as:

`GET /sequencing/counts?group_by=programme&platform=PacBio&since=...&until=...&date_basis=run_start`

would answer the first turn directly, returning programme, platform, count, date basis, and cache sync time.

Include `programme` in `mlwh_study_overview`. It already carries `name`, `accession_number`, `faculty_sponsor`, and `data_access_group`; adding `programme` would let a per-study pass group by programme without a second call.

Provide the global platform/date-scoped enumeration called for in Problem Query 03 (a `/runs` or `/products` list filterable by `platform` and a date window, with a stable cross-platform run/product identifier). Without it, any "platform X over period Y" question stays a full-catalogue fan-out.

Finally, offer a people directory or resolvable role membership so the study ↔ person graph can be traversed in both directions rather than person-first only.
