# Problem Query 02: Study 7556 CRAM TSV With Manual QC

## Initial Query

> Write a tsv of [supplier_sample_name, study_accession_number, manual_qc, irods path] where type=cram, target=1, study_id=7556. (For test purposes, write it as a temp file and clean it up afterwards)

## Approach I Took

I used only the MLWH MCP server surface for the initial data attempts. I interpreted `study_id=7556` as the LIMS study id and `type=cram` as the `file_type=cram` suffix filter supported by the iRODS and manifest tools.

The main path was:

1. Resolve study `7556` with `mlwh_resolve_study`.
2. Confirm the study accession and context with `mlwh_study_overview`.
3. Count CRAM iRODS rows with `mlwh_count_irods_paths_for_study` using `file_type=cram`.
4. Inspect `mlwh_irods_paths_for_study` using `file_type=cram`.
5. Inspect `mlwh_study_manifest` using `with_irods=true` and `file_type=cram`.
6. Check `mlwh_sample_detail` and `mlwh_sample_progress` for one returned sample to see whether `manual_qc` or `target` appeared in a sample-level response.
7. Create a scratch TSV under `.tmp/agent/`, verify it had the expected tabular shape, and delete it immediately.

The useful facts found were:

- Study `7556` resolves to `HG_WC11383_JAGUAR_Genomes`.
- Study accession number: `EGAS00001007659`.
- `mlwh_study_overview` reported `840` samples, `840` libraries, `886` data objects, and `8` runs.
- `mlwh_count_irods_paths_for_study(study_lims_id="7556", file_type="cram")` returned `886`.
- `mlwh_study_manifest(study_lims_id="7556", with_irods=true, file_type="cram")` returned rows with `supplier_name`, sample accession, run/lane/tag, and `irods_path`.

The first manifest rows showed the answerable part of the requested TSV shape:

- `JAG0013`, `EGAS00001007659`, `/seq/illumina/runs/49/49280/lane3/plex1/49280_3#1.cram`
- `JAG0030`, `EGAS00001007659`, `/seq/illumina/runs/49/49280/lane3/plex2/49280_3#2.cram`
- `JAG0048`, `EGAS00001007659`, `/seq/illumina/runs/49/49280/lane3/plex3/49280_3#3.cram`

For the temp-file part, I wrote a small probe file at a generated path like `.tmp/agent/problemquery02.MXkjoX.tsv`, verified it contained one header plus three data rows, and removed it. I left `manual_qc` blank in that probe because none of the MCP responses exposed a `manual_qc` field. I did not produce a full final TSV because that would have implied the missing `manual_qc` and `target=1` parts had been satisfied.

## Problems With The MCP Server Offerings

The closest endpoint was `mlwh_study_manifest`, because it combines study metadata, supplier/sample fields, and CRAM paths. It still does not expose `manual_qc`.

The sample-level endpoints did not solve that gap. `mlwh_sample_progress` exposes a rolled-up `qc` value such as `pass`, `fail`, or `pending`, but that is not the same thing as a requested `manual_qc` field. `mlwh_sample_detail` also did not expose `manual_qc`.

The MCP server did not expose a `target` field or a `target=1` filter on the manifest, iRODS path, sample, run, or study endpoints. I could not tell whether `target=1` refers to a product-metrics column, an iRODS-location property, a pipeline-specific flag, or some other MLWH concept.

The `file_type=cram` filter is a filename-suffix filter, not a true data-type column filter. That was probably good enough for the `type=cram` part of the query, but it is worth being explicit about the semantics.

There is no server-side TSV/export endpoint. Paging through all `886` rows would be possible through the manifest endpoint, but the agent would still have to assemble the file client-side and would still lack `manual_qc` and `target`.

## Attempted Workarounds

I used `mlwh_study_manifest` with `with_irods=true` and `file_type=cram` as the main workaround. It supplied `supplier_name`, the study accession from the response envelope, and `irods_path`.

I checked `mlwh_irods_paths_for_study`, but that endpoint lacks `supplier_name` and study accession. It is useful for path counts and path paging, not for the requested joined TSV.

I checked `mlwh_sample_detail` and `mlwh_sample_progress` for `JAGUAR_Genomes14619128`. `sample_progress` returned `qc: pass`, but no `manual_qc` or `target`. I avoided substituting `qc` for `manual_qc` because that would change the meaning of the output.

I created and removed a scratch TSV only as a shape/procedure test. It was not a valid answer to the original query because the missing fields were still missing.

## Remaining Doubts

I am not sure what `target=1` means in the user's intended MLWH query. It may be a column that exists in the underlying warehouse but is not exposed by the current MCP server.

I am also not sure whether `supplier_sample_name` should map exactly to the manifest/sample field called `supplier_name`. That mapping looks likely, but the MCP response does not use the requested column name.

The requested `manual_qc` could be distinct from the server's rolled-up `qc` value. The exposed `qc` field is per-sample/product roll-up logic, not a raw manual QC field.

## Improvement Ideas

Add a study-scoped product export endpoint for this exact shape, for example:

`GET /study/:id/products.tsv?file_type=cram&target=1&columns=supplier_name,study_accession,manual_qc,irods_path`

If TSV export is not wanted in the API, add the same fields to `mlwh_study_manifest` and support JSON paging with filters for `target` and QC fields.

The response documentation should distinguish raw `manual_qc`, rolled-up product `qc`, and any pipeline-specific `target` concept. If those fields do not exist in the mirrored cache, the server should return a clear unsupported-field error instead of making the caller infer absence from many partial responses.
