# Problem Query 07: Study 7568 Sample CRAM Paths With Merged Multi-Lane Products

## Initial Query

> Get a list of all the samples for study 7568. I want a list of sample names, along with EGA ID and an iRODS path to a CRAM file.

This is the same use case a user (Ian) reached for with the `wa mlwh` CLI: "a list of all the samples in study 7568 along with the path on iRODS to the CRAM for each sample". Through the MCP server it is nearly a single call — except that a subset of samples come back with no CRAM path unless the caller notices the problem and backfills them per sample. The goal here is to describe why, so this can be handled without that nudge.

## Approach I Took

I used only the MLWH MCP server surface. The requested shape — `sample_name`, `ega_id`, `irods_cram_path` — is exactly what `mlwh_study_manifest` with `with_irods=true` and `file_type=cram` is built for: one server-side join of sample identity to the product's CRAM.

The main path was:

1. `mlwh_resolve_study(7568)` → `HG_WC11378_IBD-RESPONSE_BGE Genotyping`, accession `EGAS00001007775`, programme `Human Genetics`, sponsor `Carl Anderson`.
2. `mlwh_study_overview(7568)` → `samples_total: 732`, `samples_with_data: 732`, `data_objects: 732`, `runs: 6`, `libraries: 732`, `library_types: ["BGE"]`, `cache_synced_at: 2026-07-06T08:24:58Z`. So every one of the 732 samples has study-scoped data.
3. Size the manifest: `mlwh_count_study_manifest(7568)` → `780`. And `mlwh_count_irods_paths_for_study(7568, file_type=cram)` → `732`. The three figures disagree: `780` products, `732` CRAM objects, `732` samples. That grain mismatch is the whole problem.
4. `mlwh_study_manifest(7568, with_irods=true, file_type=cram)`. The manifest is ordered by `(id_run, position, tag_index, name)`, so the earliest run sorts first. The first `96` rows are run `49348`, lanes `1` and `2`, tags `1`–`48`, and **every one of them has no `irods_path` key at all**. Rows from run `49606` onward are populated, e.g. `/seq/illumina/runs/49/49606/lane1/plex1/49606_1#1.cram`.
5. Pick one blank sample, `IBD_BGE14619080`, and ask the per-sample route: `mlwh_irods_paths_for_sample("IBD_BGE14619080")` → exactly one row:
   - `irods_path: /seq/illumina/runs/49/49348/lane1-2/plex1/49348_1-2#1.cram`
   - `id_product: a0678c5b817173c0012bbf08cfef92970f2a6d89d239c5a603390a3d2f8213fb`
   - `id_run: 0`, `id_sample_tmp: 0`, `name: ""`, `platform: Illumina`
6. `mlwh_count_lanes_for_sample("IBD_BGE14619080")` → `2`. The sample was sequenced on two lanes of run `49348`, and its CRAM is the single **merged** `lane1-2` object, which carries its own composite `id_product` hash.
7. Check whether the run route could backfill instead: `mlwh_count_irods_paths_for_run(49348)` → `33` (all CRAM), while `mlwh_count_samples_for_run(49348)` → `92`. `mlwh_irods_paths_for_run(49348)` returns lane `3`/`4`/`5` single-lane objects (e.g. `49348_4#13.cram`, and a `plex888` control) — all with `id_sample_tmp: 0` and `name: ""`, and none of them the `lane1-2` merged CRAMs that study 7568's samples actually have.

The arithmetic closes cleanly: `780` manifest rows = `684` populated single-lane rows + `96` empty rows (`48` samples × `2` lanes). `732` study CRAM objects = `684` single-lane CRAMs + `48` merged CRAMs. `732` samples = `684` single-lane samples + `48` two-lane merged samples. So the manifest join leaves exactly `48` samples with no CRAM path, even though all `48` have a CRAM.

To finish the requested list I had to run `mlwh_irods_paths_for_sample` for each of the `48` run-`49348` samples, merge the merged-CRAM path back in, and collapse each sample's two lane rows into one. That produced the complete `732`-row list.

## Problems With The MCP Server Offerings

The manifest's iRODS join cannot see merged multi-lane products. `mlwh_study_manifest` is grained one row per single-lane product `(id_run, position, tag_index)`, and `with_irods` is a LEFT JOIN to the iRODS mirror on that single-lane product's `id_iseq_product`. When lanes are merged, the archived CRAM is one composite object with its own `id_iseq_product` hash, which matches neither single-lane row, so `irods_path` comes back empty. This is systematic for any multi-lane/merged product, not a data gap: the CRAM exists.

The merged iRODS row is unattributable through the study- and run-scoped list routes. For `IBD_BGE14619080` the merged object reports `id_run: 0`, `id_sample_tmp: 0`, and `name: ""`. It is scoped to the study (it is included in the study CRAM count of `732`), so `mlwh_irods_paths_for_study` lists it — but with no sample name or `id_sample_tmp` it cannot be tied back to a sample from that list. And because its `id_run` is `0`, it is excluded from `mlwh_irods_paths_for_run(49348)` entirely; the rows that endpoint does return for the run carry no sample identity either. Only `mlwh_irods_paths_for_sample` finds it, because that route walks sample → products → iRODS by product membership and the caller already supplied the sample name.

The gap is silent. The manifest emits an empty `irods_path` with no flag or reason, and nothing in the response says "48 of these products have a CRAM that this join can't reach". The only signal is that `mlwh_count_irods_paths_for_study(cram)` = `732` while the manifest yields only `684` populated rows — a discrepancy the caller has to notice and reconcile by hand. `mlwh_study_overview` compounds the trap: it correctly reports `732`/`732` samples with data and `732` data objects, so availability looks perfect, yet the tool that actually carries the path can only deliver `684` of them.

Detecting which samples are affected is itself unsupported. There is no filter for "manifest rows with no iRODS match" and no "samples whose CRAM is a merged product". I identified the `48` only because all the empty rows happened to be one run (`49348`) and the counts reconciled. A study whose merged products were scattered across several runs would be much harder to detect and backfill correctly.

## Attempted Workarounds

The working route was `mlwh_study_manifest(with_irods=true, file_type=cram)` for the `684` single-lane samples, plus a per-sample `mlwh_irods_paths_for_sample` call for each of the `48` run-`49348` samples to recover the merged CRAM, then collapsing each affected sample's two lane rows into one. That is the "nudge" — an extra detection-and-backfill step the caller must know to perform.

To find the affected set I paged the manifest for empty `irods_path` rows and grouped them by sample; equivalently, they are the samples on the multi-lane run (`49348`), or the shortfall between `mlwh_count_irods_paths_for_study(cram)` (`732`) and the count of distinct samples with a populated manifest path (`684`).

I checked the run route as an alternative backfill and rejected it: `mlwh_irods_paths_for_run(49348)` returns `33` objects that are neither the study's samples nor carry sample identity, so it cannot map run-`49348` samples to their merged CRAMs.

## Remaining Doubts

I am relying on all the empty manifest rows belonging to a single run and on the arithmetic (`780 = 684 + 96`, `732 = 684 + 48`) to conclude that exactly `48` samples are affected. I did not page all `780` rows to prove no other run contributes empties, though the counts leave no room for it.

I do not know whether a sample can ever have both a single-lane CRAM and a merged CRAM (which would double-count), nor whether `id_run: 0` / `id_sample_tmp: 0` / `name: ""` is always the shape of a merged iRODS row or is data-dependent. The `33` run-level objects with `name: ""` suggest that even some single-lane pooled/control products lack sample identity in the mirror, so the missing-identity problem may be broader than merged products alone.

## Improvement Ideas

The best fix is to make `mlwh_study_manifest`'s `with_irods` resolve each product's CRAM the way `mlwh_irods_paths_for_sample` does — through the sample → product → iRODS linkage, including composite/merged products — so a multi-lane sample gets its merged CRAM and the per-lane rows collapse to one. Then this query is a single call with no backfill.

Short of that, the manifest should make the gap explicit: an `irods_unmatched: true` (with a reason such as `merged_multilane`) on each affected row, and an envelope counter such as `products_without_irods`, so the caller sees the `48` without reconstructing them from counts.

The study- and run-scoped iRODS lists should populate `name` and `id_sample_tmp` for merged products by resolving through the product → sample linkage, so `mlwh_irods_paths_for_study` and `mlwh_irods_paths_for_run` can attribute merged CRAMs to samples instead of returning `id_sample_tmp: 0` / `name: ""`.

A purpose-built export for this exact, common request would remove the trap entirely:

`GET /study/:id/sample-crams` → one row per sample: `sample_name`, `ega_id`, `irods_cram_path`, already handling merged products and one-CRAM-per-sample de-duplication.

Finally, the `mlwh_study_manifest` tool description should call out merged multi-lane CRAMs as the common cause of an empty `irods_path`; today it only says "a product with no matching iRODS object has irods_path empty", which reads like missing data rather than a join that cannot reach an object that exists.
